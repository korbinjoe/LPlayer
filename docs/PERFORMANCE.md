# LPlayer 0.10.0 性能走查

文中 `artifacts/` 路径指本机生成的测量记录，未纳入源码仓库。复现检查入口见根 README；以下结果对应各次记录的源码快照。

本次从 0.9.4 的实际源码建立基线，检查播放与精确跳转、键盘输入、缩放拖动、进度预览、列表封面与静音动态预览、控制面板、目录与字幕发现、观看记录。优化重点是移除主线程阻塞，避免连续输入产生过期任务，并保留精确定位、视频质量和所有现有功能。

## 已落地的改变

| 路径 | 发现的问题 | 处理 |
| --- | --- | --- |
| 列表动态预览关闭、主视频跳转 | 预览的 OpenGL renderer 销毁阻塞主线程约 195–418 ms | 先从界面解绑并暂停，保留原 GL context，在串行后台队列锁定该 context 销毁 renderer，再销毁播放 core；等待全部退休 core 释放后结束检查 |
| 打开视频、加载目录、匹配字幕 | 目录枚举、自然排序与字幕匹配占用界面线程 | 明确选中的视频立即启动；目录和字幕分两个后台通道发现，每个通道只保留活动任务和最新目标；补全列表不重载当前视频 |
| 列表滚动、封面查询 | 可见行反复在主线程读取文件身份与可读性 | 后台读取已授权文件的元数据，合并可见行请求，校验文件替换与请求代次；主线程查询直接使用快照 |
| 连续移动进度条预览 | 每次移动重置等待时间，移动期间迟迟没有新图 | 保留首个 80 ms 调度期限，只替换最新目标；同文件首轮预解码可完成，过期结果不能显示；等待新图时保留上一张图并标记加载中 |
| 连续按键、按钮调整 | 引擎状态回传前，下一次输入可能从旧音量、倍速或字幕延迟开始计算 | 在界面保存即时目标值，按输入累积；引擎确认实际属性并交付状态后，才清除对应版本的目标，旧确认不覆盖新输入 |
| 引擎事件和位置回传 | 繁忙时重复排队唤醒、位置回调与跳转计时器 | 合并重复唤醒和连续的纯位置快照；暂停、跳转、加载、片尾与错误仍按顺序交付；按住快进复用采样计时器 |
| 鼠标移动、播放状态更新 | 反复重建自动隐藏计时器、播放图标、面板行与未改变的文字 | 延长已有计时器期限；复用视图和图标；按相关状态变化更新面板；缓存实际原生滑块几何、提示文字测量与快捷键查找表 |
| 缩放拖动 | 高频输入需要避免额外布局、文字测量和排队 | 保留已有最新画面目标合并与不变属性跳过；提示与布局只在实际状态变化时更新；验证松手不继续惯性移动、复原正确 |
| 观看记录 | 每次保存都在主线程编码 JSON、原子写盘 | 内存状态即时更新，后台单写入器仅保留最新快照；进入无痕、休眠、正常退出时完成保存；清空后旧任务不能恢复历史 |

授权仍在主线程的文件访问管理器中处理，后台只使用本次已授权范围的不可变快照。单文件沙盒权限不会因后台枚举扩大。同目录列表保持自然顺序、只读当前层。封面缓存继续限制为 24 MiB / 128 张，文件身份快照最多 256 项；列表仅为可见行解码，动态预览仍只有一个静音引擎。隐藏、后台和主视频跳转会停止对应的预览工作。

## 前后对比

以下为同一台 Apple M1 / 16 GiB / macOS 15.6 上顺序执行的受控测试，环境记录见 `artifacts/performance-0.10.0/environment.json`。UI、预览与历史微基准使用 `swiftc -O`；实际 App 使用 release 构建。早期引擎与跳转脚本未指定优化级别，属于默认 `-Onone`，其绝对帧率不能直接当作 release 包性能；追加分段对照统一使用 `-O`，并保留旧数据。

UI 与记录数据是固定次数操作的 CPU 耗时，不是播放 FPS，也不是每次真实操作均需表中总时间。三次运行的数据使用中位数；预览生命周期、元数据延迟和实播样本保留各次原始结果。

| 测量 | 0.9.4 | 0.10.0 |
| --- | ---: | ---: |
| 预览关闭 / 暂停的主线程耗时 | 195–418 ms | 0.01–0.44 ms |
| 1,000 次列表可见行更新与封面查询 | 591.18 ms | 6.81 ms |
| 上述查询的主线程文件元数据读取次数 | 9,000 | 0 |
| 模拟每次元数据读取延迟 20 ms 时，一次可见行更新 | 94.18 ms | 0.09 ms |
| 1,000 次鼠标触发控制栏显示 | 19.94 ms | 0.669 ms |
| 1,000 次暂停状态更新 | 63.26 ms | 6.122 ms |
| 快捷面板打开时，1,000 次进度更新 | 1,655.62 ms | 141.74 ms |
| 1,000 次重复状态提示更新 | 1.95 ms | 0.293 ms |
| 50,000 次快捷键命令匹配 | 3,237.19 ms | 7.71 ms |
| 10,000 次进度条悬停位置映射 | 1,093.28 ms | 1.57 ms |
| 400 次历史保存的主线程提交 | 244.00 ms | 17.44 ms |
| 持续 60 Hz 移动期间，首张进度预览到达 | 1,212.68 ms | 631.74 ms |

持续悬停测试中，旧版直到停止移动才开始输出；新版移动期间即可输出。最终目标仍精确解码到 29 秒，像素与独立解码结果一致。新版开始真正处理移动中的预览，不能据此声称预览解码 CPU 消耗降低。

在受控的繁忙队列中，1,000 次引擎唤醒由 1,000 次排队事件处理变为 1 次；1,004 次位置与控制状态提交由 1,004 次界面回调变为 5 次，所有暂停与跳转状态边沿保留。10,000 次快进调度加取消只创建 2 个计时器。它们验证排队行为，不代表通常播放有同等数量的冗余任务。

## 实播与正确性

- 最终完整 AppKit 控制器检查：80 项断言、12 组场景。实际加载十二个合成 MKV，检查先播放后补列表、最新打开优先、繁忙 API 队列下连续与反向输入、原生精细滚动事件、延迟字幕恢复、加载中手动关闭及明确外挂优先，以及无痕期间历史和授权文件不变。两次实际片尾事件验证新目录尚在扫描时，旧片自动连播不会抢走打开请求；空目录结果能正确结束等待状态。
- 控件与快捷键检查：16,988 项断言，包含左右手、面板上下文、修饰键组合、原生滑块几何变化、自定义快捷键和语言刷新。目录发现另有 36 项断言。
- 预览检查：39 项，覆盖实际封面、精确预览像素、同路径文件替换、可见行取消、滚动与生命周期、真实静音 GPU 动画，以及 10,000 项队列仅创建 3 个可见原生行视图。
- 核心逻辑 13 组、文件访问 23 项、画面几何 13 组通过。历史后台写入 12 项通过，包含清空不被旧写入恢复、隐私边界和最后进度落盘。
- 引擎检查覆盖真实硬件解码与变动的 framebuffer 像素、精确跳转及最终目标、暂停/继续状态、缩放、窗口尺寸、连续替换、自然片尾和缺失文件失败。检查读取独立测试窗口自己的 GL buffer，不读取用户屏幕。

4K 样本为本地合成的 **3840×2160、HEVC Main10、30 fps、8 秒 SDR** 视频，实际使用 VideoToolbox。追加的发布优化级别 `-O` 配对中，旧版约 **30.07 fps**、最终版约 **30.05 fps**；双方各呈现 180 个新帧，解码、输出和 VO-delay 丢帧计数增量均为 0，五项实际渲染与硬解检查均通过。实际 backing 均为 2560×1440，测试窗口可见状态的心跳记录均为 100%。最终源码的实际 MKV 片尾、替换和缺失文件回归另有 35 项通过。

分段记录表明，双方共同的主要绘制等待来自 `flushBuffer`：约占绘制耗时的 82%–84%，最终版 p95 22.05 ms、最大 28.07 ms；实际 mpv render 的 p95 约 5.35 ms，update 的 p95 不足 0.003 ms。主线程心跳缺口与长绘制时间重叠。稳定区间每次绘制都有实际新帧，未发现无新帧重复绘制或明显回调积压。这次对照没有发现引入的 4K 回退，也没有证明普遍提高帧率；原后端的主线程垂直同步等待仍是后续渲染架构优化方向。

此前最终源码的一次未优化编译检查通过 18/19 项：硬件解码、实际变动像素、状态与输入确认通过，但帧率预算失败。约 6.26 秒呈现 149 个新帧，约 **23.80 fps，低于设定的 25 fps 门槛**；解码丢帧增量为 0，输出丢帧增量为 16，最大新帧间隔 564.82 ms，p95 61.76 ms。这个不利结果完整保留，不能将其表述为全部通过，也不能直接当作 release 包的稳定吞吐；发布模式对照未复现该长缺口，仍不足以据此认定原失败的唯一原因。

此前候选样本约 6.25 秒呈现 189 个新帧，约 30.23 fps，区间内 decoder、output、VO-delay 丢帧计数增量均为 0；新帧间隔 p95 44.24 ms。这说明短样本有显著波动，不能取最好一次代表稳定保证。测试窗口位于现有窗口后方，调度与遮挡可能影响结果，但尚不能据此归因或忽略失败。Main10 也不代表完成 HDR 正确性验证。

1080p 长 GOP 样本的帧间隔和播放中连续跳转耗时存在运行间波动。渲染调度探索阶段的一次配对中，旧版 29.85 fps / 输出丢帧增量 0，候选版 28.76 fps / 增量 8；两者解码丢帧增量均为 0。暂停单次精确跳转中位数约 258 → 254 ms，但连续播放跳转有变慢的样本。因此不宣称普遍提高视频帧率或所有文件精确跳转更快，原始数据和不利结果均保留。

追加的两组交错对照没有证明“持有渲染通知直到实际绘制”的收益：有、无此调度都出现过超时未观测到成对重启的检查，各通过 67/70 项，另有一次无调度版本发生桌面帧间隔抖动。不能据小样本认定因果；最终版撤回这项没有明确收益的额外状态，恢复原有渲染通知转发，保留已测得收益的事件、界面与预览优化。具体各次结果和对应源码哈希见引擎报告。

## 边界与后续

长 GOP、B 帧、高分辨率素材的精确定位仍要从可用关键帧解码，不能保证瞬间到达。精确跳转检查将观察期限由旧脚本的 1.45 秒明确改为 2.2 秒：旧版和新版都曾超出原期限；输入节奏、目标与精确模式不变，报告保留实际延迟。

首个动态预览的 core / GL 初始化仍是同步 API。追加分段测量中，三个独立冷进程的预览初始化中位数 44.24 ms、最大 70.83 ms；先创建主播放引擎后，九次预览初始化中位数 8.69 ms、最大 10.03 ms，核心准备仅约 2.11 ms，其余主要为 GL 和对象创建。这更接近实际 App 的初始化顺序，本轮保留现有构建方式。此前独立进程出现过一次 266 ms 异常样本，未在分段检查中复现。此检查只测空闲初始化，不覆盖首次媒体解码或 shader 工作，也使用固定语言排除个人偏好读取，不能承诺每次首预览都没有停顿。

物理触控板手感、所有编码格式、网络卷、长时间功耗、多显示器与 HDR 不由这些短合成样本覆盖。现有渲染后端仍为 OpenGL。

## 安装验证

普通本地版已使用 `scripts/build-app.sh` 构建并原子安装为 **0.10.0 / build 20**，原版备份路径保存在 `build-install.log`。`verify-release.py` 校验了 16 个源码与最终 App 集成快照一致、release 与打包 Mach-O UUID 一致、完整签名有效，以及独立的 0.8.0 沙盒预览包未被修改。结果见 `release-verification.json`。

安装后已正常退出旧进程并启动新版；`NSRunningApplication` 确认启动完成，Launch Services 返回实际运行版本 0.10.0 / build 20，记录见 `runtime-verification.json` 与 `runtime-verification.txt`。没有强制退出进程。
